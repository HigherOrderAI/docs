title: "Vendor Intake"
description: "Multi-step intake wizard that computes an Assessment Tier live, pre-fills from the Vendor Database, and routes each request to Reviewers and Approvers"
---

A four-step wizard for business teams that need a new vendor or product. As the requester fills out exposure details — data types, deployment model, AI usage, integrations — the platform computes a preliminary **Assessment Tier** in real time and shows which review path the request will take. Requests are then routed to configured Reviewers and Approvers who move each one through the workflow.

## What it does

- Walks the requester through four steps: **Scenario**, **Context**, **Exposure**, **Review & Submit**.
- Computes an **Assessment Tier** (Low / Medium / High / Critical) live during the Exposure step, with contributing factors shown as chips.
- Pre-fills vendor metadata from the **Vendor Database** when the requester selects a known vendor.
- Routes the submitted request to the tenant's configured Intake Reviewers and Intake Approvers for triage and decision.
- Supports admin soft-delete of stale requests.

<Note>
**Assessment Tier is a different concept from the validated Risk Band.** Assessment Tier is a declared, intake-time label that sets the review depth. The Risk Band (six-band scale) is produced later, once a formal assessment analyzes evidence. See [Risk Scoring Methodology](/concepts/risk-scoring).
</Note>

## Inputs

The wizard collects:

- **Scenario.** One of three intake paths:
  - **New vendor — still evaluating options** (compare up to four candidates)
  - **New vendor — vendor already chosen**
  - **Existing vendor — new product or feature**
- **Context.** Use-case description, Team (Engineering, Sales, Marketing, Finance, HR / People, Legal, Customer Success, Operations, Executive, Other), Scale of rollout (under 10 users / 10–100 / whole company), Timeline (Exploring / 3 months / 30 days / Already in trial).
- **Exposure.** Data types (Health, Financial, Source code / IP, Customer PII, Employee PII, Business data), Data scope, Deployment model, Passive capture (yes / no), AI usage, Integrations.
- **Review.** Owner name and email.

### Vendor Database pre-fill

On the Scenario step, the vendor selector is backed by the [Vendor Database](/vendor-database). Picking a known vendor pre-fills the vendor name, domain, and (for existing-vendor requests) product details. The intake detail page also embeds a **Vendor Intelligence** panel drawn from the database, so a reviewer sees the vendor's known posture in context without leaving the request.

If the vendor is not yet in the database, the requester can trigger a research job from the same selector — the vendor will be added to the database and linked to the intake once research completes.

## Assessment Tier and routing

The tier drives assessment depth and SLA:

| Tier | Review path | SLA |
|---|---|---|
| **Low** | Automated brief, no analyst review | Immediate |
| **Medium** | Analyst review with targeted output package | 2 weeks |
| **High** | Full assessment with document collection, legal + security sync | 4 weeks |
| **Critical** | Executive sign-off required, full dossier, security leadership flagged | Same-day escalation |

The **Assessment Tier** badge is shown on the Review step and on the request detail page. It replaces the previous "Risk Score" label.

## Outputs

After the requester submits, the confirmation screen shows the Request ID and the Assessment Tier. The request lands in the review workflow.

### Request detail page

Opens on click from any request list. The detail page shows:

- Requester and scenario summary
- Assessment Tier with contributing factors
- Vendor Intelligence panel pulled from the Vendor Database (if the vendor is linked)
- Activity timeline: create → review → approve / reject / conditional approve
- Reviewer and Approver actions available based on the current user's role

### My Requests

Every user sees their own submitted requests in **My Requests**. Admins additionally see a soft-delete control on each row — deleted requests are hidden from the list but can be recovered by support.

## Intake Configuration

**Vendor Intake → Intake Configuration** (`/vendor-intake/settings`) is where admins wire up the workflow:

- **Intake Reviewers** — users who can move a request into review. Assigned via the Permissions system (`intake.review` permission).
- **Intake Approvers** — users who can approve, reject, or conditionally approve a request (`intake.approve` permission).

Each role card lists the currently assigned users with a count badge; admins add and remove users from within the card. Both roles are system roles — they exist by default and cannot be deleted, though the users assigned to them can be changed at any time.

## Limitations

- Assessment Tier reflects **declared** exposure. Once documents are uploaded and analyzed, the validated Risk Band on the vendor profile takes precedence.
- The Vendor Database is a shared catalog. If your vendor is missing, research is asynchronous — expect hours, not seconds, for the profile to complete.
- Soft-deleted requests do not have a self-service restore action; restoration is a support-side operation.
- Requests can only be reviewed by users with the `intake.review` or `intake.approve` permissions. Assigning these permissions is done via Roles & Permissions or via the Intake Configuration page.
